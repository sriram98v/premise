# PREMISE alignment profiling — formats guide

This directory holds the benchmark + profiling deliverables for the alignment
optimization work on `feat/code-optim`. It doubles as a short primer on the
**industry-standard performance formats** used here.

Benchmarks live in `benches/alignment.rs`; run them with `cargo bench --bench alignment`.

---

## 1. Criterion.rs — statistical microbenchmarks

[Criterion](https://bheisler.github.io/criterion.rs/book/) is the de-facto Rust
microbenchmark harness. Unlike a stopwatch, it runs each benchmark thousands of
times and applies **bootstrap resampling** to report a *distribution*, not a
single number, so tiny regressions are detectable above noise.

**What it emits** (under `target/criterion/<group>/<bench>/`):

| File | Format | Contents |
|---|---|---|
| `new/estimates.json` | JSON | point estimates + 95% confidence intervals for `mean`, `median`, `std_dev`, `slope` |
| `new/sample.json` | JSON | every raw timing sample (iters, times) — re-analyzable |
| `report/index.html` | HTML+SVG | interactive per-bench **PDF/violin** plot, iteration regression line, outlier classification |

**Key concepts to know**
- **Median vs mean**: median is robust to outliers (OS scheduling hiccups); Criterion shows both. We headline the median.
- **95% CI**: the `[lower – upper]` band. If two runs' CIs don't overlap, the difference is real.
- **A/B baselines**: `--save-baseline <name>` snapshots a run; a later `--baseline <name>` prints the **% change + a p-value** per bench (Welch's t-test). This is the canonical before/after workflow — we use `before` as the baseline id.
- **Throughput**: with `Throughput::Bytes`/`Elements`, Criterion also reports MiB/s or elem/s.

```bash
cargo bench --bench alignment -- --save-baseline before   # snapshot
# … make changes …
cargo bench --bench alignment -- --baseline before        # compare vs snapshot
```

## 2. Flamegraph — where time goes, visually

A [flamegraph](https://www.brendangregg.com/flamegraphs.html) (Brendan Gregg)
visualizes sampled call stacks. **x-axis = share of samples** (NOT time order);
**y-axis = stack depth**. A wide frame = a function the profiler caught running
often = a hot spot. Click to zoom; Ctrl-F to search.

We generate it **in-process** with the [`pprof`](https://crates.io/crates/pprof)
crate wired into Criterion as a custom profiler, so it needs **no `perf` and no
sudo** (it samples via the `ITIMER_PROF` signal at 100 Hz). This sidesteps this
box's `perf_event_paranoid=2`.

```bash
cargo bench --bench alignment -- --profile-time=15 phase/process_read_pairs
# → target/criterion/phase/process_read_pairs/200/profile/flamegraph.svg
```

- `reports/flamegraph-baseline.svg` — before optimization.
- `reports/flamegraph-optimized.svg` — after (compare `powf`/`error_prob` width).

## 3. pprof protobuf — the portable profile format

[`pprof`](https://github.com/google/pprof) is Google's profile interchange
format: a gzipped protobuf (`.pb`) consumable by the `pprof` tool, `speedscope`,
and others. Same sampled data as the flamegraph, but portable and queryable
(top functions, call graphs, diff between two profiles).

```bash
PPROF_OUT=pb cargo bench --bench alignment -- --profile-time=15 phase/process_read_pairs
pprof -http=: reports/profile-baseline.pb          # interactive web UI
pprof -top   reports/profile-baseline.pb           # text: hottest functions
pprof -diff_base reports/profile-baseline.pb reports/profile-optimized.pb   # before/after diff
```

`.pb` files: `reports/profile-baseline.pb`, `reports/profile-optimized.pb`.
